# v0.3.0 → v0.3.1 更新時の確認事項

[English](v0.3.1-upgrade.md) | 日本語

保存形式の移行は不要です。既存の公開APIのシグネチャを維持し、SimpleQueueとGroupQueueへ `WaitInitializeWithError() error` を追加しています。詳細な保存仕様と利用制約は [compatibility.md](compatibility_ja.md)、実行可能な使用例は [usage_example_test.go](../usage_example_test.go) を参照してください。

## アプリ側で確認すること

| 項目 | 変更・注意点 | 必要な対応 |
|---|---|---|
| 初期化 | ファイル操作・JSON解析・decoderの失敗をerrorで通知。自動のpanic・ログ・アラートは行わない | consumerを先に起動し、WaitInitializeWithErrorがnilの場合だけproducerを開始する |
| 従来の待機API | WaitInitializeは完了待ちのみ。成功を返すAPIではない | 初期化結果を確認する呼び出しを新APIへ変更する |
| 運用中の障害 | 起動成功後にもI/O等のerrorは発生する | 投入・取得・UpdateIndex・closeのerrorを捨てず、管理側と監視へ通知する |
| ページ再利用 | 保存済み進捗が進むまで投入が待つ場合がある | 処理後にUpdateIndexし、consumerを動かしたままproducerの終了を待つ |
| Length() | channel内の件数。consumerが保持する処理中項目は含まない | 0件だけで処理完了と判断しない |
| 一括取得の0・1件 | 0件はErrQueueOption、1件は取得後にlazyを待たず戻る | 取得上限は1以上にする |
| Groupのcallback | 処理・index更新のerrorを返す。callback失敗後も進捗更新を試みる従来動作を維持 | 未完了のまま残したい処理は、明示的に処理して成功後にUpdateIndexする |
| errorの識別 | 正常にcloseしたGroupへの投入はIsErrQueueClose、存在しない子はIsErrQueueNotFoundで判定できる | エラー文字列の比較を避ける。記録済み障害が優先される場合がある |
| UpdateIndex | nil・別インスタンス・後退するMessageを拒否。同じ最新進捗は再書き込みしない | 取得したMessageを使用し、子ごとに連続して完了した範囲まで保存する |
| close | 二重CloseQueueはpanicせず、2回目以降のCloseIndexもnilになる | 重複呼び出しの検出や、最初のclose失敗の確認を2回目の戻り値に頼らない |
| Groupの重大な障害 | 子の障害をGroup全体へ通知 | 他の子だけで継続できると仮定しない |

新APIのnilは、呼び出し時点の確認結果です。全復旧項目の業務処理完了や、以後の正常動作を保証しません。初期化途中でconsumerが業務処理に失敗した場合の通知・停止手順も、[起動・終了の説明](compatibility_ja.md)に従って確認してください。

一括投入・処理のerrorは、一部が受け付け・処理済みの状態でも発生し得ます。無条件に全件再試行せず、業務IDや処理記録で照合してください。設定・codec・Tの変更は、ライブラリ更新と同時に行わないようにしてください。

## NFSを使用する場合

確認済みの利用条件は、SimpleQueue、2048件×3ページ、50件一括・10ms周期、NFS、SetFSync()未使用です。

既存形式には永続化された世代番号がなく、復旧はページ内容・件数・循環index・更新時刻を使用します。更新時刻が一致して履歴を区別できない場合、全件処理済みでも初期化エラーになることがあります。任意の時刻改変・逆転を安全に判定できる保証もありません。

本番相当のNFSで、少なくとも次を確認してください。

- ページ境界・周回末尾・未完了0／1／50／2048件超での停止・再開と、件数・値・順序。
- NFS接続断、クライアント／サーバー再起動、ホスト切替の影響。
- 実データ量での投入・進捗保存遅延、起動時間と最大メモリ。
- 初期化失敗時の通知・受付停止、業務処理の再配信・重複への対応。

開発環境のローカル領域でのテスト・性能測定は、NFS上の性能・耐久性を保証しません。SetFSync()未使用ではO_SYNCを要求せず、有効化だけでmtimeの曖昧さやデータとindexの原子性が解決するものでもありません。CloseQueueで、NFS上で応答しないI/Oまで中断できる保証はありません。

今回の待機API追加による定常性能低下を示す根拠は、追加確認では得られていません。これはv0.3.0からの変更全体やNFSの性能保証とは区別してください。

## 停止・更新・再開

1. 新規受付を止め、consumerを稼働させたままproducerの終了を待つ。
2. CloseQueueを呼び、consumerで残件を処理し、成功した範囲のUpdateIndexを確認する。Length()==0だけで完了と判断しない。
3. consumer終了時にCloseIndexを呼び、closeのerrorも確認する。
4. 完全停止したディレクトリ全体を、データ・index・mtimeの精度を維持して退避する。Groupでは全子を含め、退避先をGroup直下へ置かない。
5. 独立したコピーを同じ設定・codec・Tで開き、未完了範囲を照合する。調査用コピーから本来の業務処理を実行しない。
6. 旧版を停止した状態で新版を起動する。同じ保存先を両版で共有しない。consumer起動後にWaitInitializeWithErrorを確認し、成功時だけ投入を再開する。
7. 初期化エラー、投入待機、処理中件数、進捗保存、重複・欠落を監視する。

範囲外のqueue.N、短いindex、不正JSON等を検出しても、自動削除や設定変更で読み込ませないでください。原本を保全して調査します。旧版で既に上書きされた項目は、新版へ更新しても復元できません。

## 切り戻しとリリース

保存形式が同じでも、v0.3.0へバイナリを戻すだけで正しく復旧できる保証はありません。旧版には既知の復旧・ページ保護の不具合が残っています。

更新後の投入や外部処理が発生した後に、更新前の退避データへ戻すと、新規データの消失や処理の重複が起こり得ます。受付・業務ID・処理記録を照合する手順を準備し、稼働中のファイルへバックアップを上書きしないでください。

リリース時には、新規の本体ファイル（特にrecovery.goとqueue_state.go）、テスト、testdataのfixtureも含めてcommitしてください。公開対象のcommitでCIを通し、そのcommitへ新しいv0.3.1 tagを付けます。公開済みtagは上書きしません。ルートgo.modのGoバージョンはライブラリのリリース番号ではなく、module pathの変更も不要です。

現在のCIはbranch push／PRが対象で、tagだけのpushでは実行されません。tag対象commitの成功を確認してください。公開後は利用側でv0.3.1を取得してbuild/testし、ローカルreplaceを参照しただけの状態と区別します。bench/go.modのreplaceは、通常のtask go:benchで現在のソースを測定するために維持します。
