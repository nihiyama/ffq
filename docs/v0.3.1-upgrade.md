# Upgrading from v0.3.0 to v0.3.1

English | [日本語](v0.3.1-upgrade_ja.md)

No storage-format migration is required. Existing public API signatures are preserved, and `WaitInitializeWithError() error` has been added to SimpleQueue and GroupQueue. See [compatibility.md](compatibility.md) for storage and operational constraints, and [usage_example_test.go](../usage_example_test.go) for runnable examples.

## Application Checks

| Area | Change or constraint | Required action |
|---|---|---|
| Initialization | File-operation, JSON-parsing, and decoder failures are reported as errors. The library does not automatically panic, log, or alert | Start the consumer first; start producers only after WaitInitializeWithError returns nil |
| Legacy wait API | WaitInitialize only waits for completion and cannot indicate success | Use the new API where startup must check the result |
| Runtime failures | I/O and other operations can fail after successful startup | Check enqueue, dequeue, UpdateIndex, and close errors; notify the coordinator and monitoring |
| Page reuse | Enqueue may wait until progress has been saved | Call UpdateIndex after processing; keep the consumer running while waiting for producers to finish |
| Length() | Counts channel contents, excluding messages held by the consumer | Do not infer processing completion from zero alone |
| Bulk limits of zero or one | Zero returns ErrQueueOption; one returns after the first item without waiting for lazy | Use a positive batch limit |
| Group callbacks | Processing and index-update errors are returned. The previous attempt to acknowledge after callback failure is preserved | If failed work must remain pending, process explicitly and call UpdateIndex only after success |
| Error identification | Enqueue on a normally closed GroupQueue is recognized by IsErrQueueClose; missing children by IsErrQueueNotFound | Avoid error-string comparisons. Recorded failures can take precedence |
| UpdateIndex | Rejects nil, foreign-instance, or backward Messages. Repeating the latest progress skips the write | Use the dequeued Message and acknowledge only the contiguous completed prefix of each child |
| Close | Repeated CloseQueue no longer panics, and repeated CloseIndex returns nil | Do not use a repeated close to detect duplicate calls or establish that the first close failure was resolved |
| Fatal Group failures | A child's failure is propagated to the GroupQueue | Do not assume other children can continue independently |

A nil result from the new API reflects the state observed at the call. It does not guarantee that all recovered messages have finished business processing or that future operations will succeed. Review [startup and shutdown handling](compatibility.md), including notification and cancellation when the consumer encounters a business-processing failure during recovery.

Bulk enqueue or processing can return an error after some work has already been accepted or processed. Do not retry an entire batch unconditionally; reconcile business IDs and processing records. Avoid changing configuration, codecs, or T at the same time as the library upgrade.

## NFS Deployments

The reported production configuration is SimpleQueue, 2048 items × 3 pages, batches of 50 at a 10ms interval, NFS, and no `SetFSync()`.

The existing format has no persisted generation number. Recovery uses page contents, item counts, the circular index, and modification times. If equal timestamps make histories indistinguishable, initialization can fail even when all items have been processed. Arbitrary timestamp modification or reversal is not guaranteed to be detected safely.

Validate at least the following on production-like NFS:

- Stop/reopen behavior at page and cycle boundaries, with 0, 1, 50, and more than 2048 pending items; verify counts, values, and order.
- NFS connection loss, client/server restarts, and host failover.
- Enqueue and progress-write latency, startup time, and peak memory with representative data.
- Notification and admission control on initialization failure, and handling of replayed or duplicate business operations.

Local-storage tests and benchmarks do not establish NFS performance or durability. Without `SetFSync()`, the library does not request `O_SYNC`; enabling it alone does not resolve timestamp ambiguity or make data and index updates atomic. `CloseQueue()` does not guarantee cancellation of unresponsive NFS I/O.

Additional checks found no evidence of a steady-state slowdown caused by the new wait API. This is separate from evaluating the full v0.3.0 change set or guaranteeing NFS performance.

## Stop, Upgrade, and Restart

1. Stop accepting new work, then wait for producers to finish while keeping the consumer running.
2. Call CloseQueue. Let the consumer process remaining messages and verify UpdateIndex for completed work. Do not infer completion from Length()==0 alone.
3. Call CloseIndex when the consumer exits, and check close errors.
4. Back up the entire directory after a complete shutdown, preserving data, index, and modification-time precision. Include all Group children, and do not place the backup directly under the Group root.
5. Open an independent copy with the same configuration, codec, and T, and reconcile the pending range. Do not execute real business side effects from the inspection copy.
6. Start the new version with the old version stopped. Do not share the directory between versions. Start the consumer, check WaitInitializeWithError, and resume producers only after success.
7. Monitor initialization errors, enqueue waits, in-flight work, saved progress, duplicates, and missing items.

Do not automatically delete unexpected queue.N files, short indexes, or invalid JSON, or change settings to force recovery. Preserve the originals and investigate. Upgrading cannot recover items already overwritten by the old version.

## Rollback and Release

An unchanged storage format does not guarantee safe recovery by simply switching the binary back to v0.3.0. The old version retains known recovery and pending-page protection bugs.

Restoring a pre-upgrade backup after new enqueues or external side effects can lose new data or repeat business operations. Prepare reconciliation using acceptance records, business IDs, and processing records. Do not overwrite live files with a backup.

Include new implementation files, especially recovery.go and queue_state.go, tests, and testdata fixtures in the release commit. Run CI on the exact commit to publish, then create a new v0.3.1 tag on that commit. Do not overwrite published tags. The Go version in the root go.mod is not the library release number, and the module path does not need to change.

The current CI runs for branch pushes and pull requests, not tag-only pushes. Verify a successful run for the tagged commit. After publication, fetch v0.3.1 in a consuming project and build/test it without mistaking a local replacement for the published release. Keep the replace directive in bench/go.mod so that normal task go:bench runs measure the current checkout.
